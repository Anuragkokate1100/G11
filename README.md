# TrackBill AI — Shared Frontend, Backend and Database

This project is organized as **one frontend folder**, **one Spring Boot backend**, and **one MySQL database** for both Tractor Owner and Farmer roles.

## Project layout

- `frontend/` — canonical source for both roles' HTML, CSS, JavaScript and images.
- `backend/` — one Spring Boot application containing both owner and farmer APIs, authentication, services, repositories and JPA models.
- `database/original_dump/` — the supplied SQL export preserved as a backup/reference. It contains multiple SQL files with overlapping table names; do not import every file blindly.
- `database/README.md` — database setup and migration notes.

The Maven build copies `../frontend` into the packaged app's `/static` resources. This avoids maintaining a second source copy under `backend/src/main/resources/static` while still letting Spring Boot serve the frontend.

## Requirements

- JDK 21
- Maven 3.8+
- MySQL 8.x

## Configure MySQL

1. Back up your existing `trackbill_ai` database before making changes.
2. Open `backend/src/main/resources/application.properties`.
3. Configure `spring.datasource.url`, `spring.datasource.username`, and `spring.datasource.password`, or set `DATABASE_URL`, `DATABASE_USERNAME`, and `DATABASE_PASSWORD` environment variables.
4. Keep both roles pointed to the same database URL/schema (`trackbill_ai` by default).
5. `spring.jpa.hibernate.ddl-auto=update` currently lets Hibernate create/update mapped tables. For a production deployment, use reviewed migrations and set an appropriate schema-management policy.

**Do not import all SQL files from `database/original_dump/` into a live database without reviewing them.** The dump includes singular/plural table-name variants and possibly overlapping schemas. Preserve a backup and identify the tables used by your current application first.

## Run

From a terminal:

```bash
cd backend
mvn clean spring-boot:run
```

Then open:

- `http://localhost:8080/tractorlogin.html` — shared login page; choose Tractor Owner or Farmer.
- `http://localhost:8080/farmer-register.html` — farmer registration.
- `http://localhost:8080/tractorhome.html` — Tractor Owner dashboard after owner login.
- `http://localhost:8080/farmerhome.html` — Farmer dashboard after farmer login.

Serve the frontend through Spring Boot for the simplest setup. If using VS Code Live Server, confirm CORS settings and API base URL are configured correctly.

## Login and data separation

- Both roles use the same running Spring Boot application and MySQL database.
- Farmer authentication endpoints are under `/api/auth/farmer/**`.
- Farmer crop endpoints are under `/api/farmer/**` and require a Farmer token.
- Existing owner APIs continue under their existing paths and require an owner token.
- Sharing a database does not mean a farmer can read owner-private records. Keep ownership and role checks on the backend.

## Current implementation status and honest limitations

The archive contains the existing Tractor Owner module plus these Farmer features wired to backend endpoints:
- Registration creates a BCrypt-hashed account but returns no JWT; login is a separate action.
- Farmer-only crop CRUD and farmer profile endpoint.
- Farmer-only income/expense CRUD and period/monthly summaries, stored separately from owner expenses.
- Weather lookup/5-day forecast through Open-Meteo (no API key; network access required).
- Gemini farming assistant using the farmer's own saved crop context; requires `GEMINI_API_KEY` and reports API errors rather than inventing answers.
- Tractor service requests, cancellation while pending, owner-side request review/status changes, and database-backed notifications generated by these events.
- Farmer bills shown only after a tractor owner explicitly links an existing bill to the farmer's registered email. The original billing schema has no payment-status field, so the UI does not claim a bill is paid or unpaid.
- Income/expense reports from saved transaction records.

Known limitations:
- The farmer bills page cannot infer which farmer a legacy bill belongs to; a tractor owner must link the bill using the new owner API. Payment status is not tracked in the existing billing model.
- The owner service-request API is available, but no owner-side visual request-management page has been added; use the API documented below.
- Weather service and Gemini depend on external network/API availability. No weather values or AI responses are fabricated.
- Browser UI has basic CRUD and print support; PDF export, full pagination, richer charts, automated weather alerts, and notifications for every possible business event remain future work.

Verification: Maven is not installed in this environment, and no live MySQL instance or API credentials were supplied. Therefore Java compilation, database-backed integration tests, real weather calls, Gemini calls, and cross-role regression tests could not be executed here. The source was inspected and edited, but do not treat unexecuted tests as passed.

## Farmer API additions

All `/api/farmer/**` routes require a Farmer JWT. `/api/owner/**` routes require a Tractor Owner JWT.

- `POST /api/auth/farmer/register` — creates account; intentionally returns `token: null`.
- `POST /api/auth/farmer/login` — issues a Farmer JWT after credential validation.
- `GET /api/auth/farmer/me` — current Farmer profile.
- `GET|POST /api/farmer/crops`; `PUT|DELETE /api/farmer/crops/{id}` — farmer-scoped crop CRUD.
- `GET|POST /api/farmer/transactions`; `PUT|DELETE /api/farmer/transactions/{id}` — income/expense CRUD.
- `GET /api/farmer/transactions/summary?start=YYYY-MM-DD&end=YYYY-MM-DD` — actual income, expenses and net balance.
- `GET /api/farmer/reports/monthly?start=YYYY-MM-DD&end=YYYY-MM-DD` — monthly totals from saved transactions.
- `GET /api/farmer/weather?location=Baramati` — Open-Meteo current conditions and 5-day forecast. Omit `location` to use the saved village/district/state.
- `POST /api/farmer/ai/chat` with `{"message":"How should I monitor my sugarcane crop?"}` — requires `GEMINI_API_KEY`.
- `GET|POST /api/farmer/service-requests`; `POST /api/farmer/service-requests/{id}/cancel` — service requests.
- `GET /api/owner/service-requests`; `PATCH /api/owner/service-requests/{id}/status?status=ACCEPTED` — owner request queue/status.
- `GET /api/farmer/bills` — only bills explicitly linked by an owner.
- `POST /api/owner/bill-links/{billId}` with `{"farmerEmail":"farmer@example.com"}` — links an existing bill owned by the authenticated owner to a registered farmer.
- `GET /api/farmer/notifications`; `PATCH /api/farmer/notifications/{id}/read`; `POST /api/farmer/notifications/read-all`.

Example farmer transaction:
```json
{
  "transactionType": "EXPENSE",
  "category": "Fertilizer",
  "amount": 1250.00,
  "transactionDate": "2026-10-26",
  "description": "Fertilizer for sugarcane field",
  "farmOrCrop": "East field / Sugarcane"
}
```

## Configuration

Set `DATABASE_URL`, `DATABASE_USERNAME`, `DATABASE_PASSWORD`, `JWT_SECRET` (a random secret of at least 32 bytes), and optionally `GEMINI_API_KEY` as operating-system environment variables. `.env.example` is a template only; Spring Boot does not automatically load it. Do not commit real credentials. Before applying `backend/db/migration/V1__create_farmer_portal_tables.sql`, back up the database and confirm the existing `billing` and `tractor_owner` tables exist; this migration adds farmer tables and a bill-link table without rewriting existing owner records.
